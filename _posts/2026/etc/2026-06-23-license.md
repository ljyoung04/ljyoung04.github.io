GitHub에 코드를 공개할 때 라이센스를 붙이지 않으면, 기본적으로 저작권자가 모든 권리를 가진다.
즉 다른 사람이 코드를 볼 수는 있어도, 복사/수정/배포/상업적 사용을 해도 된다는 허락은 아니다.

GitHub public repository의 경우 GitHub 약관에 따라 다른 사용자가 저장소를 보고 fork할 수는 있지만, 이것이 오픈소스 라이센스를 의미하지는 않는다.
오픈소스로 공개하고 싶다면 저장소 루트에 `LICENSE`, `LICENSE.md`, `LICENSE.txt` 같은 파일을 두는 것이 일반적이다.


## 라이센스 계열

오픈소스 라이센스는 크게 permissive, weak copyleft, strong copyleft, public domain 계열로 나눠서 보면 이해하기 쉽다.

| 계열 | 특징 | 대표 라이센스 |
| --- | --- | --- |
| Permissive | 출처와 라이센스 고지만 지키면 비교적 자유롭게 사용 가능 | MIT, Apache-2.0, BSD |
| Weak copyleft | 특정 파일/라이브러리 단위로 공개 의무가 생김 | MPL-2.0, LGPL |
| Strong copyleft | 파생물 전체를 같은 라이센스로 공개해야 할 수 있음 | GPL, AGPL |
| Public domain 계열 | 가능한 한 권리를 포기하거나 조건을 거의 두지 않음 | Unlicense, CC0 |

## 자주 쓰는 라이센스

| 라이센스 | GitHub 검색 키워드 | 핵심 |
| --- | --- | --- |
| MIT | `MIT` | 가장 단순한 permissive 라이센스. 저작권/라이센스 고지만 유지하면 상업적 사용, 수정, 배포가 가능하다. 특허 조항은 따로 약하다. |
| Apache License 2.0 | `Apache-2.0` | MIT처럼 자유도가 높지만, 명시적인 특허 사용 허락이 포함된다. 기업/상업 프로젝트에서 선호되는 편이다. |
| BSD 2-Clause | `BSD-2-Clause` | MIT와 비슷하게 단순하다. 저작권 고지와 면책 고지를 유지해야 한다. |
| BSD 3-Clause | `BSD-3-Clause` | BSD 2-Clause에 원 저작자/프로젝트 이름을 홍보에 함부로 쓰지 말라는 조건이 추가된다. |
| GPL v3 | `GPL-3.0` | 강한 copyleft. 배포하는 파생 소프트웨어도 GPL로 공개해야 할 수 있다. 소스 공개 의무가 핵심이다. |
| LGPL v3 | `LGPL-3.0` | 라이브러리용 copyleft. 라이브러리 자체 수정분은 공개해야 하지만, 이를 사용하는 큰 프로그램은 다른 라이센스로 배포 가능하다. |
| AGPL v3 | `AGPL-3.0` | GPL보다 강하다. 네트워크 서비스로 제공하는 경우에도 수정된 소스 공개 의무가 생긴다. SaaS 회피를 막기 위한 라이센스다. |
| MPL 2.0 | `MPL-2.0` | 파일 단위 weak copyleft. MPL 파일을 수정하면 그 파일은 공개해야 하지만, 전체 프로젝트를 같은 라이센스로 묶지는 않는다. |
| Unlicense | `Unlicense` | 가능한 한 public domain에 가깝게 공개한다. 조건이 거의 없다. |
| CC0 1.0 | `CC0-1.0` | public domain dedication. 코드보다는 데이터, 문서, 샘플 리소스에 쓰이는 경우가 많다. |

## 빠른 선택 기준

### 그냥 자유롭게 쓰게 하고 싶다

`MIT`를 쓰면 된다.

가장 짧고 이해하기 쉽다.
개인 프로젝트, 예제 코드, 작은 라이브러리에 무난하다.

### 특허 리스크까지 조금 더 신경 쓰고 싶다

`Apache-2.0`이 적합하다.

MIT보다 길지만 특허권 허락과 특허 소송 시 권리 종료 조항이 들어 있다.
회사에서 쓰거나 외부 기여자가 많은 프로젝트라면 MIT보다 Apache-2.0이 더 명확할 수 있다.

### 수정한 코드도 반드시 공개하게 하고 싶다

배포 프로그램이면 `GPL-3.0`, 네트워크 서비스까지 포함하고 싶으면 `AGPL-3.0`을 고려한다.

다만 copyleft 라이센스는 사용자가 부담을 느낄 수 있고, 다른 라이센스와의 호환성 문제도 생길 수 있다.
라이브러리에 강한 copyleft를 붙이면 채택률이 낮아질 수 있다.

### 라이브러리는 쓰게 하되, 라이브러리 수정분은 공개하게 하고 싶다

`LGPL-3.0` 또는 `MPL-2.0`이 후보가 된다.

`LGPL`은 라이브러리 단위, `MPL`은 파일 단위로 생각하면 된다.
전체 앱을 강제로 같은 라이센스로 묶고 싶지는 않지만, 원본 코드 개선분은 공유되길 원할 때 쓴다.

### 코드가 아니라 문서/이미지/데이터를 공개한다

소스코드에는 보통 소프트웨어 라이센스를 쓰고, 문서/이미지/데이터에는 Creative Commons 계열을 많이 쓴다.

- 출처 표시만 요구: `CC-BY-4.0`
- 같은 조건 공유 요구: `CC-BY-SA-4.0`
- 권리 포기에 가깝게 공개: `CC0-1.0`

## GitHub에서의 사용법

GitHub는 저장소의 라이센스 파일을 감지해서 저장소 상단에 표시한다.
복잡한 문구를 섞어 넣으면 감지가 안 될 수 있으므로, 가능하면 표준 라이센스 전문은 `LICENSE` 파일에 그대로 두고 추가 설명은 `README.md`에 적는 것이 좋다.

저장소 검색에서는 `license:` qualifier를 쓸 수 있다.

```text
license:mit
license:apache-2.0
license:gpl
```

`license:gpl`처럼 계열 키워드를 쓰면 GPL v2, GPL v3 같은 관련 라이센스가 함께 검색된다.

## 주의할 점

- 라이센스를 나중에 바꾸는 것은 가능하지만, 이미 배포된 이전 버전의 라이센스까지 마음대로 회수할 수는 없다.
- 외부 기여를 받는 프로젝트라면 기여 코드도 같은 라이센스로 들어오는지 명확히 해야 한다.
- 다른 오픈소스 코드를 가져와 쓰는 경우, 내 프로젝트 라이센스와 호환되는지 확인해야 한다.
- `README`에 "free"라고 적는 것만으로는 충분하지 않다. 명확한 라이센스 파일을 두는 것이 좋다.
- 상표권, 보증, 책임 제한은 라이센스마다 다르다. 중요한 프로젝트라면 전문가 검토가 필요하다.
