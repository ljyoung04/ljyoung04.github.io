커널 취약점을 공부하면서 느꼈지만, 어떤 프로그램에서 취약점을 찾아내려면 그 프로그램에 대한 이해가 선행되어야 하는 것 같다. 

그래서 운영체제를 직접 만들어보는 것이 도움이 될 것 같다고 생각했고, 러스트를 배워보고 싶기도 했기에 찾아보던 중 https://os.phil-opp.com/ko/ 이런 블로그를 찾을 수 있었고 직접 따라서 해보기로 했다.

이 시리즈에서는 실습과 실습 중 모르는 부분에 대한 정리나 트러블 슈팅에 대해서만 정리해둘 것이다. 자세한 설명은 해당 블로그를 참조하자.

## 러스트로 Freestanding 실행파일 만들기

```bash
cargo new blog_os --bin --edition 2024
```
`blog_os`는 프로젝트 이름으로, 아무거나 상관없다.
`--bin`인자는 cargo에게 실행 파일을 만들겠다고 알려주고,
`--edition 2024` 인자는 cargo에게 러스트 2024에디션을 사용할 것이라 알려주는 것이다.

## no_std
기본 상태의 크레이트는 암시적으로 러스트 표준 라이브러리를 링크한다. `no_std`속성을 통해 표준 라이브러리가 링크되지 않게 해준다.

no_std를 추가하고 `cargo build`를 하면 다음과 같은 오류가 발생한다.

```
error: cannot find macro `println` in this scope
 --> src/main.rs:4:5
  |
4 |     println!("Hello, world!");
  |     ^^^^^^^

error: `#[panic_handler]` function required, but not found

error: unwinding panics are not supported without std
  |
  = help: using nightly cargo, use -Zbuild-std with panic="abort" to avoid unwinding
  = note: since the core library is usually precompiled with panic="unwind", rebuilding your crate with panic="abort" may not be enough to fix the problem
```


이런 오류가 뜨는 이유는 다음과 같다.

1. println 매크로를 제공하는 표준 라이브러리를 링크하지 않았기 때문이다.
2. 패닉 시 호출되는 함수가 존재하지 않는다.

> 컴파일러는 패닉이 일어날 경우 panic_handler 속성이 적용된 함수를 호출하도록 한다. 표준 라이브러리가 그 함수를 제공하지만 no_std 환경에서는 직접 설정해줘야 한다.
{: .prompt-info } 

블로그 글에서는 `error: language item required, but not found: eh_personality` 에러가 출력된다고 하는데 나는 보이지 않는다. 아마 3번째 에러가 해당 에러를 의미하는 것으로 보인다.

> 러스트는 패닉이 일어났을 때 스택 되감기를 통해 스택에 살아있는 각 변수의 소멸자를 호출한다. 이 동작은 복잡한 과정을 통해 이루어지며, 운영체제마다 특정한 라이브러리를 필요로 한다. 블로그에서는 해당 이유로 이 기능을 사용하지 않는다.
{: .prompt-info } 

## 패닉 시 호출되는 함수 구현

```rust
// in main.rs

use core::panic::PanicInfo;

/// 패닉이 일어날 경우, 이 함수가 호출됩니다.
#[panic_handler]
fn panic(_info: &PanicInfo) -> ! {
    loop {}
}
```
PanicInfo 인자는 패닉에 대한 자세한 정보를 가진 구조체이다. 

```toml
[profile.dev]
panic = "abort"

[profile.release]
panic = "abort"
```
Cargo.toml에 위 내용을 추가하자.

이렇게 하고 build를 해보면 여전히 에러가 발생한다.

```
error: using `fn main` requires the standard library
  |
  = help: use `#![no_main]` to bypass the Rust generated entrypoint and declare a platform specific entrypoint yourself, usually with `#[no_mangle]`
```


## start 속성

대부분의 프로그래밍 언어는 런타임 시스템을 가진다. 이들은 프로그램 실행 이전에 초기화 되어야 하기에 main 호출 이전에 먼저 호출된다. 

> 런타임 시스템(런타임 환경)이란 프로그램이 실행되는 동안 필요한 환경과 동작을 제공하는 소프트웨어 하위 시스템이다.
{: .prompt-info }

러스트 표준 라이브러리를 링크하는 대부분의 러스트 실행 파일의 경우, 프로그램 실행 시 C 런타임 라이브러리인 crt0에서 실행이 시작된다.

우리의 실행 파일은 러스트 런타임이나 crt0에 접근할 수 없기에, 우리가 직접 프로그램의 시작 지점을 지정해야한다. 

## 실행 시작 지점 덮어쓰기

```rust
#![no_std]
#![no_main]
use core::panic::PanicInfo;

#[panic_handler]
fn panic(_info: &PanicInfo) -> ! {
    loop {}
}

#[unsafe(no_mangle)]
pub extern "C" fn _start() -> ! {
    loop {}
}
```
no_main 속성을 통해 일반적인 실행 시작 호출 단계를 사용하지 않겠다고 선언한다.
따라서 main 함수가 필요없다.

`extern "C"`는 이 함수가 러스트 함수 호출 규약 대신 C 함수 호출 규약을 사용하도록 한다.

다시 `cargo build`를 하면 링커 오류가 발생한다.

```
error: linking with `cc` failed: exit status: 1
```

## 링커 오류
링커는 컴파일러가 생성한 코드를 묶어 실행파일로 만들어준다. 실행 파일 형식은 운영체제마다 다르기에 각 운영체제는 자신만의 링커가 있고 링커마다 다른 오류 메세지를 출력한다.

하지만 오류의 근본적인 원인은 동일한데, 링커는 이 프로그램이 C 런타임 시스템을 이용할 것이라고 가정하는 반면, 우리의 크레이트는 그렇지 않기 때문이다.

이 오류를 해결하려면 링커에게 C런타임을 링크하지 말라고 알려줘야한다. 두 가지 방법이 있는데, 하나는 링커에 특정 인자를 주는 것이고, 다른 하나는 컴파일 대상 기기를 bare metal 기기로 설정하는 것이다.

## bare metal 시스템을 목표로 빌드하기

기본적으로 컴파일러와 링커는 운영체제가 있다고 각정하고, 또한 운영체제가 C 런타임 시스템을 사용할 것이라고 가정하기 때문에 링커 오류 메세지가 출력된 것이다. 이를 피하려면 운영체제가 없는 시스템 환경에서 코드가 구동하는 것을 목표로 컴파일 해야한다.

운영체제가 없는 bare metal 시스템 환경의 예시로 `thumbv7em-none-eabihf`이 있다. 

```bash
rustup target add thumbv7em-none-eabihf
cargo build --target thumbv7em-none-eabihf
```

이제 빌드가 문제없이 잘 된다.
